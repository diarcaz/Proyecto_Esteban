# NEXUSTAFF PHASE 4.6 BETA EMPLOYEE ONBOARDING REPORT

1. **Original root cause:** Employees posted only locationId to StaffController/StaffService.create. That path created User plus UserLocationAssignment, with no Department, Position, effective dates or EmployeeAssignment. No Department/Position management endpoints or UI were exposed. The approved kiosk correctly rejected these legacy-only users.
2. **Files changed in Phase 4.6:** backend/src/adapters/dtos/onboarding.dtos.ts; backend/src/adapters/controllers/onboarding.controller.ts; backend/src/application/services/onboarding.service.ts; backend/src/app.module.ts; backend/src/application/services/staff.service.ts; backend/src/adapters/controllers/staff.controller.ts; backend/src/adapters/guards/permissions.guard.ts; backend/src/adapters/guards/roles-and-locations.guard.ts; backend/scripts/phase46-onboarding.test.cjs; backend/package.json; frontend/src/app/admin/(protected)/employees/page.tsx; frontend/src/lib/api-client.ts; frontend/tests/phase46.test.cjs; frontend/package.json; BETA_OPERATIONS.md; this report. Existing uncommitted Phase 4.5 changes were preserved.
3. **Employee creation:** Admin Employees → Create Employee → WORKER identity/status and initial six-digit PIN → Property → Department → Position → dates → Save. Email is optional in the form; the required database email receives a unique non-deliverable employees.invalid identifier if absent. Account password is random and never returned. New user and assignment are committed in one PostgreSQL transaction with an audit entry.
4. **EmployeeAssignment:** Canonical active=true record has user/property/department/position, effectiveFrom and optional effectiveUntil. A secondary UserLocationAssignment supports existing directory/admin visibility, including recovery after deactivation. It never substitutes for operational clock authority. Existing users lacking operational context can use Add Assignment without recreation.
5. **Department/Position:** New catalog and small inline create forms. PROPERTY_MANAGE required for creation. Backend resolves real property ownership and verifies both department.locationId and position.locationId/departmentId plus position.active. No submitted cross-property combination is trusted.
6. **Additional Property:** Add Assignment uses the same User and requires STAFF_EDIT on the target Property plus existing employee access and matching company. A user row lock serializes additions/deactivation. Any simultaneous active date overlap at the same Property is rejected; different Properties are allowed. SUPER_ADMIN cannot create a cross-company employee/property mismatch.
7. **Deactivation:** Changes active=false and audits without deleting context. An open shift at that Property must be closed first. Once no current active EmployeeAssignment remains, the approved resolver rejects clocking. Another Property assignment is unaffected. Existing assignment end-date editing is not implemented; create with an end date or deactivate/replace.
8. **PIN:** Uses existing bcrypt authentication and encryption utility; generic onboarding returns only the new ID. Details never return hashes, ciphertext, password or PIN. Explicit View PIN/Reset PIN use existing staff endpoints and target-aware permission checks. UI only enables actions from server capabilities, masks PIN entry and hides recovered PIN after 15 seconds. Generic staff editing now requires RESET_EMPLOYEE_PIN to change a PIN, closing a bypass through that path.
9. **Permissions:** STAFF_CREATE for onboarding; STAFF_EDIT for assignment/add/deactivate and normal editing; STAFF_VIEW for details; PROPERTY_MANAGE for Department/Position writes. Backend verifies actor role, tenant, employee access and DB-resolved target Property. Canonical routes bypass only legacy assignment-only routing checks and perform authoritative checks in the service. PIN guard keeps a preliminary permission check; the existing PIN service enforces actual employee/company/property scope. OWNER works within its company without an artificial legacy location requirement.
10. **Clock Ready UX:** Evaluated by backend using the approved active/effective/ambiguity resolver plus employee ACTIVE status and configured hash. Displayed per authorized Property. It denotes operational identity readiness, not a guarantee that the current shift state allows CLOCK_IN. Missing, future, expired, inactive or conflicting assignment context is not shown as ready.
11. **Rates:** EmployeeAssignment.rateConfigurationId is nullable. Existing WorkShift logic accepts no applicable rate and stores financial snapshot fields as null. No RateConfiguration or placeholder pay/bill/OT rate was created. The preexisting legacy User.hourlyRate schema default remains untouched and is not used/displayed as the beta work-shift rate. No schema/migration was necessary.
12. **Tests added:** 14 backend scenarios using isolated real PostgreSQL data (atomic create, approved PIN identity and full lunch cycle, legacy-only rejection, invalid department/position, foreign scope, second assignment, deactivation/expiry, forced transactional rollback, no rates, PIN permissions, concurrent overlaps and ambiguity, missing capabilities/OWNER, future/reversed dates). Four frontend rendering regressions cover server readiness, PIN capability hiding, authorized PIN controls and dependent Position options.
13. **Total passing:** 205 automated cases/scenarios: existing backend security 156, beta backend 8, Phase 4.6 backend 14, frontend 27 (15 Phase 4.1 + 3 Phase 4.2 + 5 beta + 4 Phase 4.6). Browser acceptance is additional, not included in this count. Tests use local nexustaff_test only, with fixture-scoped cleanup.
14. **Backend:** npm run build and TypeScript --noEmit passed. Existing security and beta suites passed. Local npm/npx wrappers were broken, so installed npm and project CLI entry points were invoked directly.
15. **Frontend:** Production build with explicitly supplied local API URL and TypeScript --noEmit passed. All existing Phase 4.x tests passed. Non-blocking webpack cache/npm warnings remain; ESLint was not configured.
16. **Prisma:** validate passed. No schema/migration diff. Legacy users.pin_code and index retained.
17. **Browser acceptance:** Actual Next production build + Nest backend + local PostgreSQL/Redis. Created Department and Position inline, created one WORKER, observed server Clock Ready. Added a second Property's Department/Position/assignment to the same User. Configured terminal explicitly. Completed PIN identity → CLOCK_IN → LUNCH_START → LUNCH_END → CLOCK_OUT. All four events appeared in Admin. Then deactivated Property A after closing its shift: A showed Assignment Required, kiosk rejected it, B remained Clock Ready. Database verification found one employee, two assignments (one active), four events and zero RateConfigurations. Temporary company/admin/employee/properties/departments/positions/assignments/logs and fixture Redis session keys were cleaned up. Test servers stopped. The local browser terminal pairing references the removed fixture and must be reconfigured before subsequent use.
18. **Full journey:** The functional Company/Property → Department → Position → Employee → EmployeeAssignment → PIN → clock/lunch/out → Admin attendance journey passed locally. Secure SUPER_ADMIN bootstrap remains explicit and covered by the existing beta tests; browser acceptance used an isolated admin fixture instead of bootstrapping into a populated test database.
19. **Remaining beta blockers:** No confirmed onboarding functional blocker remains. Real hosting deployment, proxy/client-IP validation, persistent Redis, PostgreSQL backup/restore policy and remote smoke acceptance remain manual deployment gates from Phase 4.5. No remote deployment is claimed. Advanced rates, payroll, invoicing, final XLSX and advanced configuration remain outside this beta scope.
20. **Final verdict: BETA FUNCTIONALLY READY** for Time & Attendance, based on the local automated and browser evidence above. Phase 5 was not started.
